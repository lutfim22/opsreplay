OPSREPLAY / 01 · Overview

OpsReplay
AI + public API + simulated IoT

Understand the incident.
Follow the evidence.

OpsReplay combines device signals and software activity in one timeline, then helps an operator investigate with AI.

The problem

A device goes offline. Was there a power change? A software change? Evidence sits in different places, and guessing too early can lead to the wrong action.

The approach

Bring the records together, keep their source labels, and ask for an explanation with evidence links and explicit uncertainty.

Think of it as a shared incident notebook: the timeline holds the records; AI helps organize questions. A human still decides what the evidence means.

OPSREPLAY / 02 · User journey

From scattered records to a clearer question

For an operator, the flow is simple: inspect → narrow the input → investigate → review.

1 · Inspect

Read the timeline. See which entries came from the simulator and which came from GitHub.

2 · Narrow

Filter the events. The AI receives every event currently visible after filtering.

3 · Investigate

Click once when live usage is approved. The server asks Gemini for structured findings.

4 · Review

Compare facts and hypotheses with their cited events before choosing a read-only check.

The completed demo used three simulated events

These are simulator records, not measurements from a physical plug. The public GitHub integration is a separate input; this AI run contained no GitHub events.

Fact

A reading or status in a submitted event.

Hypothesis

A possible explanation that can still be wrong.

Evidence link

A reference back to a submitted event; not proof of causation.

OPSREPLAY / 03 · Architecture

How the pieces fit together

The browser presents the evidence. The server handles credentials, quota checks, the AI request and result validation.

GitHub API

Fetches public commits, pull requests and workflow activity. It does not write to the repository.

Upstash Redis

Shares request counters and concurrency leases. It is not an incident or event database.

Validation

Checks the response shape and that cited event IDs belong to the submitted input. It cannot verify the model’s interpretation.

Preview access is protected by Vercel login. The application itself does not implement user accounts. Secrets stay on the server.

OPSREPLAY / 05 · Demo script

A demo you can deliver in 2–3 minutes

Present the existing successful result. Another Investigate click would create a new paid request and needs a separate decision.

0:00–0:20Set the problem

“Device records and software changes often live in different tools. OpsReplay brings them into one evidence timeline.”

0:20–0:50Show the sources

“These device events are simulated. GitHub entries are public software activity. The labels and original timestamps stay visible.”

0:50–1:15Narrow the input

“Filters define what the AI receives. Display alignment is optional and does not change the original evidence.”

1:15–1:55Show the saved AI result

“This run analyzed two power readings and an offline event. The result separates observed facts from an unconfirmed hypothesis.”

1:55–2:20Follow the evidence

“References help us trace an answer back to its input. They do not prove a cause or guarantee the model is correct.”

2:20–2:45State the boundary

“This is a protected prototype. It has no physical hardware or automatic remediation. Public AI remains off.”

Before presenting: open the saved result or recording, keep provenance labels visible, and never expose keys, tokens or browser login state.

OPSREPLAY / 06 · Technical guide

Technical guide for a new contributor

Next.js App Router · React · TypeScript · server-side Google Gemini · shared Redis quotas

Request path

  1. POST /api/investigate checks the exact feature opt-in before reading the body.
  2. Origin and payload checks run; absent Origin is allowed, so origin checks are not authentication.
  3. An atomic Redis script reserves quota before the provider call.
  4. Gemini receives the reduced JSON schema; local Zod and evidence checks validate the response.
  5. A finally block releases the concurrency lease. This UI test did not independently observe Redis key deletion.

Boundaries worth knowing

Input
200 events · 512 KiB request · 256 KiB prompt
Provider
8192 output tokens/attempt · 25 s configured deadline
Retries
Up to 3 attempts, only for transient 503/504; this run used 1
Quotas
100 global/day · 5/client/min · 15/client/day · 3 concurrent
Storage
Browser-local demo events; Redis is for quotas
Costs
Request limits and billing alerts are not hard spending caps

Offline verification

pnpm install --frozen-lockfile
pnpm lint && pnpm typecheck && pnpm test && pnpm build

Use the package manager pinned in package.json and the lockfile. These checks mock Gemini/Redis and require no live credentials. Opening GitHub activity in the running app can make public API requests.

OPSREPLAY / 07 · Release notes

What is ready — and what is still open

A successful private demo is a useful milestone. It is not approval for public AI activation.

Evidence we have

✓ Offline CI

248 tests, lint, typecheck and normal build passed.

✓ Gemini schema

One bounded reduced-schema workflow passed.

✓ Redis scenarios

Concurrency/release, quota denials and expired-lease pruning passed.

✓ Protected UI

Owner confirmed login enforcement; one UI investigation succeeded.

Remaining decisions

  1. Deployed host/IP trust, direct requests and negative quota/outage cases need further verification.
  2. Natural lease expiry, UTC rollover and failover are not fully tested.
  3. Existing immutable Production snapshots may retain previously injected secrets after configuration removal.
  4. Public access, database isolation and future AI spending need a separate release decision.
Public app: opsreplay.vercel.app (AI OFF). The verified AI Preview requires Vercel access. Use recorded evidence or owner presentation; do not weaken protection for judges.
